# The lower-triangular rank-k update on the packed 8 × 6 f64 tile

Feature: [t4a-private-gemm-x86#19](https://github.com/tensor4all/t4a-private-gemm-x86/pull/19),
unblocking the `f64` LLT cell of
[tensor4all/colmat-rs#257](https://github.com/tensor4all/colmat-rs/issues/257). Follow-up to
[2026-11-23-skylake-client-f32-gemm.md](2026-11-23-skylake-client-f32-gemm.md), whose gate
(`b84dd30`) this stacks on.

## What and why

A blocked Cholesky factorization spends about 78 % of the call at `n = 1024`, `f64` in its
trailing update, `C -= L L^T` over the lower triangle. The packed driver carried only the full
product, so colmat ran the update through the generic path and was 2.2-2.4× behind `dsyrk_` on the
same block set.

`syrk_lower_block(n, k, l, lda, c, ldc, alpha, beta, i0, rows)` updates one row block of `C`
through the same 8 × 6 tile:

* It packs that block of `L` once and walks the column blocks at or below the diagonal
  (`i0`-outer / `j0`-inner), so an A panel is not repacked per 6-row B block.
* Tiles entirely above the diagonal are skipped; the tiles that straddle it go through an
  `MR × NR` edge buffer that holds only the lower entries, so the strict upper triangle is never
  read or written.
* Depth is one panel, `k <= SYRK_DEPTH_PANEL` (192, the `kc` that `multiply` derives from an
  admitted core's 32 KiB L1). The Cholesky range is 16..=128.
* Scratch is per thread and reused: `ceil(rows / 8) * 8 * k + 6 * k` `f64`, the packed block at
  the packer's padded extent plus the RHS panel. A rejected call (gate off, `k = 0`, depth past
  the panel, zero stride, block outside `C`) returns `false` before it allocates or writes.

Row blocks are independent and each entry's `k`-sum is the same one a whole-range call makes, so
handing blocks to different threads is bit-identical to one call. That is the property colmat's
team and sequential LLT paths are compared on.

## Results

**The feature numbers below come from the consumer's harness**, which is where the block-set
decomposition lives:
[tensor4all/colmat-rs `docs/worklogs/2026-11-23-cholesky-syrk-skylake.md`](https://github.com/tensor4all/colmat-rs/blob/main/docs/worklogs/2026-11-23-cholesky-syrk-skylake.md).
This crate's own measurements are the review-commit regression check and the `dsyrk_` comparison
below them.
Host: i9-9900K (Coffee Lake client, model `0x9E`, AVX2 + FMA, no AVX-512), macOS, OpenBLAS 0.3.34,
`f64`, `n = 1024`, the 15 trailing-update steps the factorization visits.

| piece | this driver | OpenBLAS `dsyrk_` |
|---|---:|---:|
| trailing update, 15 steps | 5.71 ms | 5.68-5.79 ms |
| whole factorization, 1T, `bs = 64` | 14.04 → 6.88 ms | 6.39-6.62 ms (`dpotrf_`) |
| whole factorization, 2/4/8T | 3.840 / 2.459 / 2.970 ms | 7.109 / 5.366 / 3.827 ms |

The update is at parity with `dsyrk_` and is the whole difference between colmat's 1T before and
after columns. The multi-thread row is a *paired same-host observation*, not a controlled campaign
cell: macOS offers no CPU-set pinning, and OpenBLAS's `dpotrf_` itself slows from 1T to 2T on this
part, so part of the 2T ratio is its scaling. The 1T cell does not win: the remaining 4-6 % is the
panel solve (10 % behind `dtrsm`) plus what `dpotrf` saves inside itself, and colmat's record
shows a blocked `potrf` assembled from OpenBLAS's own `dpotf2`/`dtrsm`/`dsyrk` is 2-7 % slower
than its own `dpotrf`.

Kernel-side candidates that were tried and dropped (details and the numbers in colmat's record):

* **A B-outer loop** (pack the B panel once, sweep all row blocks) — the A pack repeats per B
  tile; `i0`-outer / `j0`-inner is what the driver uses.
* **`mc` (row block held in L2) 64/128/192/256/384/512/768/1024** against the `n = 1024` block
  set: 512, an A panel of `512 · 64 · 8` B ≈ one L2.
* **A deferred two-level update** (`k = 2 · bs`) measures 0.53 ms faster in the `syrk` set but
  needs an extra `N × bs` by `bs × bs` product per step to stay correct — about +1.1 ms. Rejected
  on the consumer side, not here.

## Regression check of the review commits

The review commits (`3984f73`, `fb51fcd`) only replace the depth literal with
`SYRK_DEPTH_PANEL`, move the thread-local to module scope and rewrite the tests, so they should be
inert. Measured anyway, on the same host, release (`opt-level = 3`, `lto = "thin"`,
`codegen-units = 1`), the same stand-alone harness against `cd7c066` and `fb51fcd`, 6 alternating
process pairings, 15 reps each, median of process medians (ms):

| cell | `cd7c066` | `fb51fcd` | ratio |
|---|---:|---:|---:|
| 15 steps, `n = 1024`, `bs = 64` | 6.181 | 6.097 | 0.986 |
| 7 steps, `n = 1024`, `bs = 128` | 5.489 | 5.364 | 0.977 |
| one `n = 960`, `k = 64` | 1.058 | 1.043 | 0.986 |
| one `n = 1024`, `k = 64` | 1.222 | 1.217 | 0.996 |
| one `n = 1024`, `k = 128` | 2.376 | 2.412 | 1.015 |
| one `n = 512`, `k = 64` | 0.305 | 0.305 | 0.998 |
| one `n = 256`, `k = 32` | 0.045 | 0.045 | 1.006 |

Every cell is inside the ±2-4 % process drift this host shows, in both directions. The supporting
check is stronger than the timings: the two binaries' `__text` disassembly is identical line for
line (75,877 lines, after normalizing crate hashes and the moved thread-local's mangled name), so
the commits generate the same code and the numbers are one program run twice.

The headline cell against OpenBLAS 0.3.34 `dsyrk_` on this host, today, through the same harness:
5.96-6.13 ms packed against 5.80-5.92 ms (ratio 1.03-1.05), three process runs. That is the
parity of the table above, inside the same drift; the absolute values sit ~4 % above colmat's
in-process 5.71 ms because this harness times the block set on its own rather than inside the
factorization. The ratio is the claim, not the absolute.

## Verification

* `cargo test --release --lib packed_avx2` — 20 passed on the i9-9900K. The syrk tests compare
  against a scalar lower update at the microtile edges (`n = 13, k = 5`), one full block
  (`96 × 64`), the depth limit (`96 × 192`), a block narrower than the microkernels and blocks of
  1/3/5/7 rows (every partial-tile path), both `Accum` and two `alpha` values, with the strict
  upper triangle and the rows outside the block asserted bit-unchanged.
* `syrk_entry_whole_range_and_partitions_are_bit_identical` runs the public entry with the
  test-only gate override on, so the success path (scratch sizing, validation, `Accum` plumbing,
  the row-block split) is covered on every AVX2+FMA host, including the GitHub runners the
  production gate excludes. `syrk_entry_refuses_and_writes_nothing_when_the_gate_is_off` and
  `syrk_entry_follows_the_production_gate` cover the refusal contract everywhere.
* `syrk_scratch_is_reused_across_calls` asserts the per-thread buffer's capacity and data pointer
  are unchanged by a second call of the same shape and by a later smaller one
  (tensor4all/faer#111).
* `cargo build --no-default-features` builds; `syrk_lower_block` carries no `std`-feature gate
  (the crate is not `no_std` and `packed_avx2` uses `std` unconditionally), so a
  `default-features = false` consumer still sees it.

## What remains unverified

* The driver's own stand-alone throughput curve is a handful of shapes (the cells above), not a
  sweep: `mc` was only explored in the consumer's harness, and the 2-8 thread numbers there are a
  paired observation, not a controlled campaign cell.
* The upper-triangle and block-split guarantees are asserted for the shapes the tests use
  (`n <= 97`, `k <= 192`); wider fuzz passes were run by review against the inner driver and
  through the entry, not by a test in this repo.
* Real Haswell hardware was not re-measured for this feature (the admitted-model test list is
  unchanged from #9); AVX-512 hosts never reach the entry.
* The in-place case (updating `C` where `L` is a view of the same buffer) is outside the safety
  contract: the consumer keeps a separate panel copy of `L`.
